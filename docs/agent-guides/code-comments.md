# Code comments

Code must explain what it does. A comment must explain a constraint or a reason that the code cannot show.

## Keep a comment when it records

- a protocol or compatibility requirement;
- a security boundary or abuse limit;
- a timing, physics, rendering, or browser constraint;
- a non-obvious product decision;
- a workaround that must remain until a named condition changes;
- asset provenance or an export requirement.

## Remove a comment when it

- repeats the next statement;
- narrates the edit history;
- explains syntax;
- contains a plan, apology, or conversation;
- records a prompt, tool action, or generated rationale;
- describes code that no longer exists;
- can be replaced with a clear name or helper.

## Writing style

Use ASD-STE100-style English where practical:

- Use short, direct sentences.
- Put one idea in each sentence.
- Use active voice.
- Use the same term for the same item.
- Avoid idioms, jokes, rhetorical questions, and vague pronouns.
- State units, limits, and conditions explicitly.

Place a comment directly above the smallest block that needs it. Do not add file headers that restate the file name.
