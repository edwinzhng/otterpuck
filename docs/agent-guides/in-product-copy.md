# In-product copy

Use plain English. Follow ASD-STE100 principles where they improve clarity. This is a style goal, not a requirement to use aerospace terminology.

## Rules

- Use short sentences. Put one instruction in each sentence.
- Use common words and active voice.
- Address the player directly only when it improves clarity.
- Name the visible control exactly as it appears.
- Start instructions with the action: “Hold Shoot,” “Choose a team,” or “Try again.”
- Use sentence case for headings and buttons.
- Keep buttons to one clear verb or verb phrase.
- Do not repeat a heading in its description.
- Do not explain mechanics that the interface can show.
- Avoid slash-separated phrases when a short sentence is clearer.
- Avoid “simply,” “just,” “obviously,” “invalid,” and blame-oriented language.
- Reject generic motivational text, feature claims, and filler that do not help the player act.
- Do not invent a control, capability, limitation, or recovery step to make copy sound complete.

## Errors

An error message must state:

1. What happened in player terms.
2. What the player can do next.

Example: “Connection lost. Rejoin the room to try again.”

Do not show raw exceptions, status codes, stack traces, or infrastructure names.

## Tutorials

- Teach one skill per step.
- Require the player to perform the skill when completion can be measured.
- Put controls on a separate short line.
- Make hints more specific than the first instruction.
- Use the player's device, handedness, and current mode when wording depends on them.
- Do not describe hidden thresholds or internal state.

## Review

Read copy at its narrowest supported width. Remove words before you reduce the font size. Check both desktop and touch variants.
